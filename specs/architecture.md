## 1. Что строим

Личный тренажёр грамматики английского по книге Raymond Murphy **English Grammar in Use, 5th edition** (145 юнитов, intermediate). Пользователь — русскоязычный, уровень около B2. Продукт некоммерческий, для себя; книга куплена.

**Сценарий использования:**
- Пользователь читает теорию юнита в книге и берёт юнит в работу — отметка в каталоге (`units.started`).
- Каждый день открывает систему на **~15 минут**. Сессия ограничена **по времени**, а не по количеству заданий: задания атомарные, сессия заканчивается, когда выходит таймер.
- Система сама выбирает задания: повторяет пройденные юниты по сроку, подтягивает слабые и, если остаётся время, вводит новые.
- Теории в системе нет, только упражнения.
- Цель: пройти книгу за **~6 месяцев** так, чтобы всё хорошо запомнилось. Потом добавить другие книги и разделы.

**Расчёт** (раздел 4.5 `rating-model.md`, посчитан при `PROMOTE_MIN_CREDIT` 0.5 и упрощённой модели сессии): при ~10 заданиях в день за 5 месяцев вводится вся книга, к полугоду ~125 из 145 юнитов держатся месяц и дольше, ~89 «освоены». Поддержка после этого — 4–5 повторений в день. Симуляция с планировщиком и текущими константами — `planner.md` §6.

**Развёртывание:** self-hosted, свой сервер, Claude API (платный отдельно от подписки). Стек: Next.js + TypeScript, данные в Supabase Postgres, ключи API и Supabase только на сервере. Без Docker. Аутентификации нет: пользователь один (несколько пользователей появятся гораздо позже).

## 2. Модули

| Модуль | Отвечает за | Вход → выход | Чего не знает |
|---|---|---|---|
| **1. Каталог** | рабочие области и их юниты: номер, точное название из книги, раздел, описание своими словами. В области может быть несколько книг | — → юниты | рейтинг и историю заданий; из состояния знает только отметку «в работе» (`started`) |
| **2. Задания** | генерация задания и его проверка, повторные попытки, лог заданий и попыток | юнит + тип → задание; задание + ответ → оценка по целевому и побочным юнитам | кто решает, его уровень, история |
| **3. Модель ученика** | всё из `rating-model.md`: оценка → свидетельства → освоение и ступень лестницы; видимый уровень, прогресс, срок повтора, «освоен» | свидетельство → новое состояние юнита; состояние + «сейчас» → уровень, прогресс, пора ли повторять | как выглядят задания, кто их генерирует, что делать с юнитом дальше |
| **4. Планировщик** | какое **следующее задание** дать: какой юнит и какой тип (`planner.md`) | юниты области (с `started`) + задания + попытки + «сейчас» → (юнит, тип) | как задания генерируются и проверяются, формулы рейтинга; понятия сессии и таймера |
| **5. Сессия** | таймер и цикл одного задания: спросить планировщик → задание → показать → проверить → записать в лог → обновить модель → следующее | длина сессии → цепочка заданий | ничего не решает и не считает сама |
| **Хранилище** | лог заданий и попыток (источник истины); «в работе» — `units.started`. Кэша состояний нет, длина сессии — в браузере | — | — |

### Поток одного задания

```
Сессия ──«что дальше?»──▶ Планировщик ──читает──▶ Модель ученика (уровни, сроки)
   │                          │
   │◀──── юнит 19, перевод ───┘
   │
   ├──▶ Задания: сгенерировать ──▶ показать пользователю ──▶ ответ
   │         Задания: проверить (повторные попытки)
   │◀──── оценка по юнитам ───┘
   │
   ├──▶ Хранилище: записать попытку в лог
   └──▶ Модель ученика: оценка → свидетельства → новые состояния юнитов
```

Таймер вышел: текущее задание можно дорешать, следующее не запрашивается. Пауза (нажатие на таймер или уход со вкладки/из окна) останавливает время сессии и закрывает задание; после конца времени её нет. Каждое задание засчитывается сразу; итог дня по юниту пересчитывается из всех его заданий за день, поэтому неважно, сколько было сессий.

### Границы между модулями

```ts
// 2 → лог: результат проверки попытки (поля — exercise-spec.md §4)
type Evaluation = OpenEvaluation | ClosedEvaluation;
// OpenEvaluation: verdict, target { status, score, … }, others { unit_id, status, score, notable, … }[], issues, …
// ClosedEvaluation: items, correct, total

// лог → 3: что засчитать (evidenceOf; правила — rating-model.md §3.1)
type Evidence = { at: number; role: "target" | "side"; type: ExerciseType; r: number /* 0..1 */ };

// 3: состояние и чтение
type UnitState = { M: number; stage: number; dueFrom: number | null; lastSeen: number | null; day: Day | null };
function update(state: UnitState, ev: Evidence): UnitState;
function level(state: UnitState, now: number): number;
function progress(state: UnitState, now: number): number;
function isDue(state: UnitState, now: number): boolean;

// 4: следующее задание (planner.md); состояния юнитов считает сам из попыток
type PlannerUnit = { id: number; position: number; started: boolean };
type PlannerExercise = { id: number; unitId: number; type: ExerciseType; createdAt: number };
type PlannerAttempt = { exerciseId: number; at: number; evaluation: Evaluation };
function nextExercise(units: PlannerUnit[], exercises: PlannerExercise[], attempts: PlannerAttempt[], now: number): { unitId: number; type: ExerciseType; tier: Tier } | null;
```

Модель ученика и планировщик — чистые функции без сети и базы.

## 3. Принятые решения

### Каталог
- Юниты называются **точно как в книге** и идут **в том же порядке**, с теми же разделами. Описания для LLM — своими словами, по смыслу главы.
- Каталог 5-го издания (145 юнитов, 16 разделов) собран в базе, в рабочей области «Grammar In Use»; исходно — из прототипа (`reference/grammar-drill.html`).

### Задания
- **Пять типов** по нарастанию сложности: gap (пропуск), choice (выбор), rephrase (перефразирование), translate (перевод с русского), free (свободный ответ). Rephrase легче translate: исходное предложение задаёт смысл и лексику. Заданного начала ответа нет — оно выдавало конструкцию.
- **gap и choice проверяются локально** по ключу, который LLM выдаёт при генерации (со всеми допустимыми вариантами). Их можно генерировать заранее пачками.
- **translate, rephrase, free проверяет LLM**, ответ строго в JSON, ссылки только на id юнитов из каталога.
- **«Верно, но без целевой конструкции»:** разбор скрыт (нет исправленного ответа, версии носителя, эталона, подсказок), целевой юнит показан как «не использован». Текст «Верно. А теперь напиши ответ с конструкцией из юнита N. Название.» формирует сервер, без примеров. Попыток сколько угодно, есть «Показать разбор». Каждая попытка оценивается независимо, предыдущий ответ в проверку не передаётся. Ошибки в побочных юнитах при этом видны.
- **Побочные юниты:** ошибки и «частично» — в общем списке правок, удачные употребления (`notable`) — строкой «Отлично», остальные верные — одной строкой «Без ошибок: …» (без кнопки «Показать все»).
- **Оценка юнита в результате:** и число 0–100, и статус с обоснованием.
- **Оспаривание** проверки — позже, отдельной фичей (`exercise-spec.md`, раздел 9).

### Области
- **Всё про область — в `content/<key>/`** (`key` — `workspaces.key`, у Grammar In Use — `grammar-in-use`): `workspace.yaml` (лестница типов с их константами, темы, переопределения констант модели), по папке на тип — md-промпты и evals (случаи, судья), `README.md` с правилами области. В коде области не зашиты: новая область — новая папка и строка в `workspaces` (`exercise-types.md`).
- **Две области:** Grammar In Use (`grammar-in-use`) и Vocabulary In Use (`vocabulary-in-use`, English Vocabulary in Use Upper-intermediate). У лексики та же лестница типов и те же константы; целевая «конструкция» — лексика юнита из раздела «## Лексика» guide, побочных юнитов нет (проверка оценивает только целевой, всё прочее — в `other_issues`), тем нет: ситуацию задаёт пункт «## Употребление» (`topics: []`). Правила — `content/vocabulary-in-use/README.md`, формат guide — `catalog-spec.md`.
- **Конфиг модели ученика и планировщика — по области:** общие умолчания (`learner/model.ts`, `DEFAULTS`) плюс `workspace.yaml` (`learner/config.ts`). Состояние юнита считается по конфигу его области; планировщик выдаёт только типы области, в её порядке и с её порогами `fromM`.
- **Проверка при старте:** у каждой области из базы есть `workspace.yaml` с допустимыми значениями (`rating-model.md` §0), у каждого её типа — нужные md, имена версий промптов не повторяются. Иначе сервер не стартует (`src/instrumentation.node.ts` → `content/index.ts`, `checkContent`).
- Файлы `content/` читаются при каждом обращении, как промпты: правка действует без перезапуска (проверка диапазонов — тоже при каждом чтении).

### Модель ученика (подробно в `rating-model.md`)
- **Две шкалы:** освоение (Эло, 0–100, меняется после каждого задания) и ступень лестницы повторений (1, 2, 4, 7, 14, 30, 60, 120 дней).
- **Прогресс** = min(видимый уровень, потолок по ступени): пока тема не держится месяц, прогресс не выше 68. **«Освоен» = прогресс ≥ 80** — отметка для сводки (счётчики, цвет строки и карты), планировщик её не использует, из практики не исключает.
- Освоение от времени не уменьшается; «тускнеет» только видимая полоска. За забывание отвечает лестница.
- Все задания юнита за день считаются как одна сессия. Раннее повторение идёт в освоение, но ступень не поднимает. Пропуски и выбор поднимают максимум до ступени «7 дней» и освоение до 50.
- Каждая попытка независимо даёт свидетельства: по целевому юниту (кроме «верно, но без целевой конструкции»; неверный ответ без конструкции — 0) и по каждому побочному с ошибкой ниже порога провала — только у юнитов в работе (текущий `started`); `notable` отмечается в разборе, но бонуса не даёт. Штрафа за повторную попытку нет, «Показать разбор» ни на что не влияет.
- Ошибка в побочном юните: освоение снижается (K_SIDE), ступень −1 (не чаще раза в день), интервал заново. Побочная роль только штрафует — ни одна шкала от неё не растёт.
- Итог сессии: только юниты, у которых сдвинулась хоть одна из трёх шкал (в видимом округлении), по `position`; счётчик заданий — все задания сессии.
- `K_TARGET = 20` (выбрано после сравнения 15–30: при 25+ «освоенных» больше не становится, а шум растёт).
- **Лог попыток — источник истины.** Состояния юнитов выводятся из него (`replay`), константы можно менять и пересчитывать всю историю.

### Платформа
- Прототип — артефакт claude.ai на подписке пользователя. Self-hosted версия — Claude API, платится отдельно (оценка: ~$0.03 за пару «генерация + проверка» на Sonnet; дешевле с кэшированием каталога в промпте, Haiku для генерации gap/choice, Batch API для заготовок).
- Аутентификации, rate limit и Docker нет: личный инструмент, один пользователь. Ключи API и Supabase живут только на сервере и в клиент не попадают.
- День для лестницы повторений считается по часовому поясу сервера (`rating-model.md`, `DAY_START_HOUR`).

### Как сейчас устроен код

- Next.js 16 (App Router), React 19, TypeScript, Drizzle ORM + postgres-js, `@anthropic-ai/sdk`, `marked` (рендер `guide`), Langfuse + OpenTelemetry (трейсинг, ниже). База — облачный Supabase (`DATABASE_URL`), ключи в `.env.local`. Тесты — только чистых модулей (модель ученика, планировщик): `npm test`, встроенный `node:test` через `tsx`.
- Вместо API-роутов — server actions `src/app/actions.ts`, ошибки возвращаются значением:
  - задания: `startExercise(unitId, type|null)` (▶ в строке юнита), `checkExercise`, `revealExercise`;
  - сессия: `nextSessionExercise(workspaceId)` — задание по планировщику, `prepareNextExercise(workspaceId)` — заготовка следующего, пока решается текущее (в памяти сервера, в базу попадает только при показе), `sessionSummary(exerciseIds)` — итог сессии;
  - каталог: `setUnitStarted(unitId, started)`.
- `src/server/catalog` — модуль доступа каталога. `src/server/exercises` — типы, схема и запись лога. `src/server/content` — содержимое областей: `settings.ts` — пути в `content/<key>/` и чтение `workspace.yaml` (без `server-only`: читают и тесты, и evals), `index.ts` — настройки по id области и проверка при старте. `src/server/tasks` — только код, папка на тип (`<type>/index.ts` — определение типа `TaskType`: `items`, `outputSchema`, `normalize`, `publicContent`, `sentences`, `parseAnswer`, `check`; md-файлы промптов — в `content/<key>/<type>/`, `exercise-spec.md` §7; подробно — `exercise-types.md`), `registry.ts` — реестр определений, `generate.ts` — один конвейер генерации на все типы, `grade.ts` — проверка по `check.by` (по ключу — локально; моделью — вызов, схема и нормализация, тексты — у типа), `define.ts` — общие детали определений (схемы, разбор ответов), `prompt.ts` — чтение md из `content/<key>/<type>/` и подстановка плейсхолдеров, `variety.ts` — данные для разнообразия генерации (план фокуса, недавние задания), `claude.ts` — вызов модели (`askJson`, system с `cache_control`; со схемой ответа — `output_config.format` json_schema и `JSON.parse`, после него у всех строк ответа рекурсивно обрезаются хвостовые «}» и пробелы (`trim.ts`: модель иногда «закрывает» JSON внутри последнего строкового поля — так было с `target_note_ru` translate после переноса в конец схемы), без схемы — терпимый `parseJsonLoose`, только для судей evals; вместе с server-side fallback — `client.beta.messages`, `fallbacks: "default"`; в metadata трейса — `output_format`). `src/server/learner` — модель ученика, планировщик, показатели для каталога и итог сессии; `config.ts` — конфиг области из умолчаний и `workspace.yaml` с проверкой диапазонов.
- **Трейсинг вызовов Claude — Langfuse Cloud.** Только трейсинг: промпты остаются в md в git, реестр промптов Langfuse не используется.
  - Каждый вызов `askJson` — отдельный трейс `generate` или `grade` с одной генерацией внутри: полный промпт (system и user), сырой ответ модели, фактическая модель (после fallback может отличаться от запрошенной — та в `requested_model`), токены с кэшем, время, стоимость (цены моделей Claude Langfuse знает сам), `stop_reason`.
  - Метаданные трейса: `call`, `type`, `prompt_version`, `unit_id`, `workspace_id`; у проверки ещё `exercise_id` и `seq` будущей попытки — `tasks/index.ts` пробрасывает их через контекст (`propagateAttributes`), а не параметрами.
  - Ошибки — та же генерация с уровнем `ERROR` и причиной в `statusMessage`: ошибка API, отказ, `max_tokens`, неразбираемый JSON.
  - Подключение — `src/instrumentation.ts` → `instrumentation.node.ts`: OTel `NodeSDK` с `LangfuseSpanProcessor` (`@langfuse/otel`, `@langfuse/tracing` v6). Режим `batched`: спаны уходят в фоне, ответ их не ждёт, недоступный Langfuse запрос не роняет. При остановке сервера трейсы, ещё не отправленные из буфера, могут потеряться — это допустимо: вызовов мало, сервер перезапускается вручную после сборки. Собственные OTel-спаны `@anthropic-ai/sdk` выключены, иначе генерация писалась бы дважды.
  - Ключи — `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL` в `.env.local`. Без ключей провайдер не регистрируется и трейсинг выключен: приложение работает как раньше, без ошибок и предупреждений.
  - Если вызов идёт внутри наблюдения Langfuse (прогон evals), генерация ложится в его трейс, а не в свой.
- **Evals — Langfuse Experiments**: настоящие вызовы промптов на фиксированных случаях с оценками; сравнивать версии промптов по цифрам, а не на глаз. Наборы генерации — `gap-generate`, `choice-generate`, `rephrase-generate`, `translate-generate`, `free-generate` (с LLM-судьёй); наборы проверки открытых ответов — `rephrase-grade`, `translate-grade`, `free-grade` (без судьи, сравнение с ожиданием кодом).
  - Области: `grammar-in-use` и `vocabulary-in-use` — наборы и код общие, случаи и судьи у каждой свои. У лексики тем нет: в случаях генерации `topic` не задан (тема пустая); в наборах проверки вместо ветки `side-error` — `collocation-error` (неверный предлог или коллокация при слове юнита), `side_errors` у всех случаев `[]`: побочных юнитов нет, `no_false_side` следит, что проверка их не назвала.
  - Запуск: `npm run eval -- <набор> <область> [--repeat N] [--report] [--dry-run] [--controls-only]` (`N` — сколько раз прогонять каждый случай, по умолчанию 1; `--dry-run` — только прочитать случаи и сверить юниты с базой, без Langfuse и вызовов модели, и сказать, сколько случаев не заполнено; незаполненные в прогон не идут). Ключи Langfuse и Anthropic — из `.env.local`.
  - `--report` — подробный отчёт для калибровки судьи: markdown `evals/reports/<набор>_<область>_<время>.md` (папка в `.gitignore`). В начале — версии генерации и судьи и средние; по каждому заданию — юнит, тема, ошибка генерации, по каждому пункту — text, answers (у choice — варианты, верный жирным), focus, explain_ru и вердикт судьи целиком (все поля и note_ru; проваленные — жирным). Вердикты целиком лежат и в Langfuse — в metadata score `judge_rule`.
  - Код набора — `evals/<набор>/index.ts` (фабрика по области: случаи, задача и оценщики — интерфейс `evals/suite.ts`). Случаи и судья — в содержимом области: набор `<тип>-<вид>` берёт `content/<область>/<тип>/evals/<вид>-cases.yaml` (у наборов генерации — `{id, unit_id, topic}`) и `<вид>-judge.md` (промпт судьи, у наборов генерации); `<область>` в команде — `workspaces.key`. Источник истины — git: запуск синхронизирует случаи в датасет Langfuse `<область>/<набор>` (upsert, пропавшие — в архив). В корне `evals/` — общий запуск `run.ts`, интерфейс набора `suite.ts` (и общее у наборов генерации: случаи, критерии области, контрольные случаи), общее у закрытых типов `closed-generate.ts`, у открытых — `open-generate.ts`, у наборов проверки — `grade.ts`, и `reports/`. Порог рейтинга в оценках проверки (`FAIL_THRESHOLD`) — из конфига области.
  - **Критерии судьи — по области:** раздел `criteria` в `generate-cases.yaml` набора — ключи критериев из тех, что знает набор (`areaCriteria`, `evals/suite.ts`); нет раздела — все. Судья области отвечает только по своим критериям, схема ответа проверяется по ним же. У лексики gap и choice — без `aux_inside` (вспомогательных глаголов в пропуске нет); у грамматики раздела нет.
  - Задача — генерация без записи в базу: тема из случая, недавних заданий нет (`generate(type, unitId, { topic, recent: [] })`; приложение тему и недавние не передаёт). Имя прогона — версии промпта генерации и судьи и время.
  - Оценки по заданию (доля прошедших пунктов): кодом — `valid_items` (утечку ответа в текст ловит судья — `judge_not_guessable`); LLM-судьёй (`claude-opus-5-5`, один вызов на задание, промпт `content/<область>/gap/evals/generate-judge.md` со своей версией, ответ — строго JSON) — `judge_rule`, `judge_key_complete` (пропущенные варианты — в comment), `judge_not_guessable`, `judge_aux_inside`, `judge_focus`, `judge_explain`. Оценки прогона — средние по каждому score. В терминал — средние и задания с проблемами по пунктам.
  - `choice-generate` — те же случаи (14 юнитов и тем, что у gap). Кодом — `valid_items`: доля из 6 пунктов, у которых 2–3 варианта, `correct` — валидный индекс, варианты не повторяются по точному тексту (trim, не `norm`: варианты, различающиеся только знаком, допустимы). Судья — `content/<область>/choice/evals/generate-judge.md` (`choice-judge-v1`), принципы те же, что у gap: ученик видит юнит, верное — по правилам юнита, вариант вне юнита верным не считается, ключ британский. Оценки: `judge_rule`, `judge_one_correct` (главная: верен ровно один вариант, иначе ученику засчитают ошибку за правильный ответ), `judge_distractors` (дистракторы — типичные ошибки по юниту), `judge_not_guessable`, `judge_aux_inside` (вспомогательные — внутри вариантов), `judge_focus`, `judge_explain`.
  - Наборы проверки (`rephrase-grade`, `translate-grade`, `free-grade`; общий код — `evals/grade.ts`). Случаи: раздел `tasks` — задания `{id, unit_id, content}` (`content` как в `exercises.content`), раздел `cases` — `{id, task, answer, expect}`, одно задание — в нескольких случаях. `expect`: `verdict`, `target` (ожидаемый `target.status`) — значение или список допустимых; `side_errors` — unit_id, которые должны оказаться в `others` со статусом `error` / `partial`, элемент может быть списком «найден любой из» (`[]` — побочных быть не должно; ключа нет — не проверяются). `--dry-run` и начало прогона показывают замечания, не исправляя их: ответ free, который отвергнет `parseAnswer`, и юниты `side_errors` не из области и книги целевого или с `exclude_as_side`. Пустой `answer` или нет `verdict` / `target` — случай не заполнен. id случая — `<юнит>-<тип>-<ветка>`, ветки `target`, `non-target`, `target-error`, `side-error`, `edge`.
    - Задача — путь приложения без записи в базу: `parseAnswer` (в том числе длина free) и `check` задания. Ответ, отвергнутый `parseAnswer`, и сбой проверки — ошибка случая (без оценок, в списке проблем), а не провал.
    - Оценки по случаю (0/1): `verdict_match`, `target_match`, `side_found` (все ожидаемые побочные найдены; только при непустом `side_errors`), `no_false_side` (нет побочных с ошибкой, не входящих ни в один элемент `side_errors`; только при заданном `side_errors`). `target_fail` — только в ветке `target-error`: результат целевого юнита по правилам `learner/evidence.ts` ниже `FAIL_THRESHOLD`, то есть ошибка дошла до рейтинга провалом. Побочный с ошибкой для `side_found` и `no_false_side` — как в модели ученика (`rating-model.md` §3.1): `error` / `partial` с баллом ниже `FAIL_THRESHOLD` (константа из `learner/model.ts`, без балла — 0.3); с баллом от порога в рейтинг не попадает и не считается ни найденным, ни лишним. Имя прогона — версия проверки и время.
    - В терминал и в отчёт — средние с разбросом и только несовпавшие случаи: ответ, ожидание, что вернула проверка (verdict, `target.status` со score, `target.fragment` с правкой и `comment_ru`, `others` с `error` / `partial` и баллом каждого — от порога помечены «не в рейтинг», `summary_ru`).
  - Наборы генерации открытых типов (`rephrase-generate`, `translate-generate`, `free-generate`; общий код — `evals/open-generate.ts`, судья — `<тип>/evals/generate-judge.md` области: `rephrase-judge-v1`, `translate-judge-v1`, `free-judge-v1`). Случаи те же, что у gap. Ошибки генерации бьют по рейтингу косвенно: задание не требует конструкции (лишние обходы), подсказывает её (незаслуженный успех), эталон неверен (проверка на него смотрит). Оценки по заданию 0/1: кодом — `valid` (прошло нормализацию), у free ещё `reference_length` (эталон в пределах `FREE_LENGTH`); судьёй (`claude-opus-5-5`, один вызов на задание, по каждому критерию `{ok, note_ru}`) — `judge_requires_target` (самый естественный ответ носителя использует конструкцию по правилам юнита, обход заметно менее естественен), `judge_no_leak` (исходник, русский текст или вопрос и `instructions_ru` не содержат конструкции и не называют грамматику; слова, без которых не обходится почти ни одно предложение, — не утечка, если это не само отрабатываемое употребление), `judge_reference` (эталон верен, с конструкцией по правилам юнита и передаёт смысл задания), `judge_focus`; у translate ещё `judge_source_natural` (русский текст не калька) и `judge_note` (`target_note_ru` верен и на «ты»), у free — `judge_prompt` (вопрос короткий, ясный, не перечисляет содержание ответа и не повторяет инструкции о длине и языке). Принципы — как у судей gap и choice: ученик видит юнит, верное — по правилам юнита, ключ британский. В отчёте — задание целиком и вердикт по каждому критерию.
  - Контрольные случаи судьи — раздел `controls` в `generate-cases.yaml` набора генерации области (всех пяти типов): `{id, unit_id, content, expect_fail}` — готовое задание с известным дефектом (как в `exercises.content`, взято из прогона, где дефект был) и критерии, которые судья обязан провалить. Генерации нет: задание сразу идёт к судье. У gap и choice задание может быть из одного пункта (судья оценивает пункты по отдельности), `valid_items` для контрольных не считается, критерий провален, если провален хоть в одном пункте. Оценка — `control_caught` (1, если провалены все критерии из `expect_fail`), отдельно от средних обычных случаев; в терминале и в шапке отчёта — сколько поймано и по каждому не пойманному ответ судьи по всем критериям. Зачем: когда текущая генерация не даёт дефекта (критерий на ней 1.00), только они показывают, что судья его поймает. При подъёме версии судьи контрольные случаи прогоняются (`--controls-only --repeat 3`), не пойманный — повод не принимать версию. Обычный прогон идёт и по ним.
  - Предел калибровки судей. `requires_target` у free (`free-judge-v4`) ловит явные дефекты контекста (нет раздражения для always + continuous, нет сожаления для wish + hadn't), пограничные — нет (нестабильно: длительное действие, которое ученику надо додумать). Дальше судей калибруем только по дефекту, реально дошедшему до пользователя; на калибровку одного судьи — один круг (правка, контрольные, обычный прогон), без подгонки по кругу.
  - В metadata каждого прогона — `commit` (хеш HEAD) и `dirty` (есть незакоммиченные изменения в `content`, `src/server/tasks` или `evals`), в шапке отчёта — строка «коммит»: по ней видно, восстанавливается ли текст версий из git. Это запись, а не запрет.
  - Повтор — один проход по всем случаям; его номер — `repeat` в metadata элемента прогона; число повторов — `repeats` в metadata прогона (не `repeat`: SDK сливает metadata прогона поверх metadata элемента). При `--repeat N` по каждому score ещё среднее каждого повтора, min и max повторов — в терминале и в шапке отчёта; в Langfuse средние повторов — оценки уровня прогона `<score>/repeat-<k>` рядом с общими. Разброс повторов — шум модели: разница версий промпта в его пределах — не улучшение. В наборах проверки на ветку 7 случаев: разница в 1–2 случая — шум, решения — по несовпадениям, устойчивым во всех повторах.
- `src/components/UnitMap.tsx` — карта юнитов (квадраты 3×3, `--map-unit`; строки раскладывает по ширине колонки сама, `ResizeObserver`), общая для страницы области и `/catalog`; разделы для неё собирает `unitMapSections.ts` на сервере.
- `src/components/exercises` — UI заданий: общее для закрытых (`Exercise.css`, `useClosedCheck`, `CheckActions`), открытые — `OpenExercise` + `OpenAttempt`, обёртки типов (`RephraseExercise`, `TranslateExercise`, `FreeExercise`).
- Пользователь запускает prod-сервер (`npm start`): после `npm run build` его нужно перезапустить, иначе работает старый код.
- Разовые проверки — временным скриптом `scripts/_x.mts` (`npx tsx --conditions=react-server --env-file=.env.local scripts/_x.mts`), потом удалить. Пробные генерации — прямым вызовом `rephrase.generate` / `check`, без записи в базу, чтобы не трогать рейтинг.

### Порядок разработки
1. **Каталог, затем задания** — сначала каркас, таблица юнитов в Supabase, модуль доступа и страница каталога (`catalog-spec.md`), затем оглавление, потом перенос тренажёра (`claude-code-prompt.md`) поверх неё: юниты с первого дня по `id`. Генерация `guide` — когда удобно, до неё в промпт идёт `summary_ru`.
2. **Хранилище и лог попыток** — данные копятся с первого дня.
3. **Модель ученика** — эталонная реализация, сценарии из `rating-model.md` как тесты. Ручной режим: юнит выбирает пользователь, прогресс и сроки уже считаются.
4. **Планировщик + сессия по таймеру** — ежедневная сессия на 15 минут.
