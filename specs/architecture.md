## 1. Что строим

Личный тренажёр грамматики английского по книге Raymond Murphy **English Grammar in Use, 5th edition** (145 юнитов, intermediate). Пользователь — русскоязычный, уровень около B2. Продукт некоммерческий, для себя; книга куплена.

**Сценарий использования:**
- Пользователь читает теорию юнита в книге и берёт юнит в работу — отметка в каталоге (`units.started`).
- Каждый день открывает систему на **~15 минут**. Сессия ограничена **по времени**, а не по количеству заданий: задания атомарные, сессия заканчивается, когда выходит таймер.
- Система сама выбирает задания: повторяет пройденные юниты по сроку, подтягивает слабые и, если остаётся время, вводит новые.
- Теории в системе нет, только упражнения.
- Цель: пройти книгу за **~6 месяцев** так, чтобы всё хорошо запомнилось. Потом добавить другие книги и разделы.

**Расчёт** (раздел 4.5 `rating-model.md`, посчитан при `PROMOTE_MIN_CREDIT` 0.5 и упрощённой модели сессии): при ~10 заданиях в день за 5 месяцев вводится вся книга, к полугоду ~125 из 145 юнитов держатся месяц и дольше, ~89 «освоены». Поддержка после этого — 4–5 повторений в день. Симуляция с планировщиком и текущими константами — `planner.md` §6.

**Развёртывание:** self-hosted, свой сервер, Claude API (платный отдельно от подписки). Стек: Next.js + TypeScript, данные в Supabase Postgres, ключи API и Supabase только на сервере. Без Docker. Аутентификации нет: пользователь один (несколько пользователей появятся гораздо позже).

## 2. Модули

| Модуль | Отвечает за | Вход → выход | Чего не знает |
|---|---|---|---|
| **1. Каталог** | рабочие области и их юниты: номер, точное название из книги, раздел, описание своими словами. В области может быть несколько книг | — → юниты | рейтинг и историю заданий; из состояния знает только отметку «в работе» (`started`) |
| **2. Задания** | генерация задания и его проверка, повторные попытки, лог заданий и попыток | юнит + тип → задание; задание + ответ → оценка по целевому и побочным юнитам | кто решает, его уровень, история |
| **3. Модель ученика** | всё из `rating-model.md`: оценка → свидетельства → освоение и ступень лестницы; видимый уровень, прогресс, срок повтора, «освоен» | свидетельство → новое состояние юнита; состояние + «сейчас» → уровень, прогресс, пора ли повторять | как выглядят задания, кто их генерирует, что делать с юнитом дальше |
| **4. Планировщик** | какое **следующее задание** дать: какой юнит и какой тип (`planner.md`) | юниты области (с `started`) + задания + попытки + «сейчас» → (юнит, тип) | как задания генерируются и проверяются, формулы рейтинга; понятия сессии и таймера |
| **5. Сессия** | таймер и цикл одного задания: спросить планировщик → задание → показать → проверить → записать в лог → обновить модель → следующее | длина сессии → цепочка заданий | ничего не решает и не считает сама |
| **Хранилище** | лог заданий и попыток (источник истины); «в работе» — `units.started`. Кэша состояний нет, длина сессии — в браузере | — | — |

### Поток одного задания

```
Сессия ──«что дальше?»──▶ Планировщик ──читает──▶ Модель ученика (уровни, сроки)
   │                          │
   │◀──── юнит 19, перевод ───┘
   │
   ├──▶ Задания: сгенерировать ──▶ показать пользователю ──▶ ответ
   │         Задания: проверить (повторные попытки)
   │◀──── оценка по юнитам ───┘
   │
   ├──▶ Хранилище: записать попытку в лог
   └──▶ Модель ученика: оценка → свидетельства → новые состояния юнитов
```

Таймер вышел: текущее задание можно дорешать, следующее не запрашивается. Каждое задание засчитывается сразу; итог дня по юниту пересчитывается из всех его заданий за день, поэтому неважно, сколько было сессий.

### Границы между модулями

```ts
// 2 → лог: результат проверки попытки (поля — exercise-spec.md §4)
type Evaluation = OpenEvaluation | ClosedEvaluation;
// OpenEvaluation: verdict, target { status, score, … }, others { unit_id, status, score, notable, … }[], issues, …
// ClosedEvaluation: items, correct, total

// лог → 3: что засчитать (evidenceOf; правила — rating-model.md §3.1)
type Evidence = { at: number; role: "target" | "side"; type: ExerciseType; r: number /* 0..1 */ };

// 3: состояние и чтение
type UnitState = { M: number; stage: number; dueFrom: number | null; lastSeen: number | null; day: Day | null };
function update(state: UnitState, ev: Evidence): UnitState;
function level(state: UnitState, now: number): number;
function progress(state: UnitState, now: number): number;
function isDue(state: UnitState, now: number): boolean;

// 4: следующее задание (planner.md); состояния юнитов считает сам из попыток
type PlannerUnit = { id: number; position: number; started: boolean };
type PlannerExercise = { id: number; unitId: number; type: ExerciseType; createdAt: number };
type PlannerAttempt = { exerciseId: number; at: number; evaluation: Evaluation };
function nextExercise(units: PlannerUnit[], exercises: PlannerExercise[], attempts: PlannerAttempt[], now: number): { unitId: number; type: ExerciseType; tier: Tier } | null;
```

Модель ученика и планировщик — чистые функции без сети и базы.

## 3. Принятые решения

### Каталог
- Юниты называются **точно как в книге** и идут **в том же порядке**, с теми же разделами. Описания для LLM — своими словами, по смыслу главы.
- Каталог 5-го издания (145 юнитов, 16 разделов) собран в базе, в рабочей области «Grammar In Use»; исходно — из прототипа (`reference/grammar-drill.html`).

### Задания
- **Пять типов** по нарастанию сложности: gap (пропуск), choice (выбор), rephrase (перефразирование), translate (перевод с русского), free (свободный ответ). Rephrase легче translate: исходное предложение задаёт смысл и лексику. Заданного начала ответа нет — оно выдавало конструкцию.
- **gap и choice проверяются локально** по ключу, который LLM выдаёт при генерации (со всеми допустимыми вариантами). Их можно генерировать заранее пачками.
- **translate, rephrase, free проверяет LLM**, ответ строго в JSON, ссылки только на id юнитов из каталога.
- **«Верно, но без целевой конструкции»:** разбор скрыт (нет исправленного ответа, версии носителя, эталона, подсказок), целевой юнит показан как «не использован». Текст «Верно. А теперь напиши ответ с конструкцией из юнита N. Название.» формирует сервер, без примеров. Попыток сколько угодно, есть «Показать разбор». Каждая попытка оценивается независимо, предыдущий ответ в проверку не передаётся. Ошибки в побочных юнитах при этом видны.
- **Побочные юниты:** ошибки и «частично» — в общем списке правок, удачные употребления (`notable`) — строкой «Отлично», остальные верные — одной строкой «Без ошибок: …» (без кнопки «Показать все»).
- **Оценка юнита в результате:** и число 0–100, и статус с обоснованием.
- **Оспаривание** проверки — позже, отдельной фичей (`exercise-spec.md`, раздел 9).

### Модель ученика (подробно в `rating-model.md`)
- **Две шкалы:** освоение (Эло, 0–100, меняется после каждого задания) и ступень лестницы повторений (1, 2, 4, 7, 14, 30, 60, 120 дней).
- **Прогресс** = min(видимый уровень, потолок по ступени): пока тема не держится месяц, прогресс не выше 68. **«Освоен» = прогресс ≥ 80** — отметка для сводки (счётчики, цвет строки и карты), планировщик её не использует, из практики не исключает.
- Освоение от времени не уменьшается; «тускнеет» только видимая полоска. За забывание отвечает лестница.
- Все задания юнита за день считаются как одна сессия. Раннее повторение идёт в освоение, но ступень не поднимает. Пропуски и выбор поднимают максимум до ступени «7 дней» и освоение до 50.
- Каждая попытка независимо даёт свидетельства: по целевому юниту (кроме «верно, но без целевой конструкции»; неверный ответ без конструкции — 0) и по каждому побочному с ошибкой или `notable`. Штрафа за повторную попытку нет, «Показать разбор» ни на что не влияет.
- Ошибка в побочном юните: освоение снижается (K_SIDE), ступень −1 (не чаще раза в день), интервал заново.
- `K_TARGET = 20` (выбрано после сравнения 15–30: при 25+ «освоенных» больше не становится, а шум растёт).
- **Лог попыток — источник истины.** Состояния юнитов выводятся из него (`replay`), константы можно менять и пересчитывать всю историю.

### Платформа
- Прототип — артефакт claude.ai на подписке пользователя. Self-hosted версия — Claude API, платится отдельно (оценка: ~$0.03 за пару «генерация + проверка» на Sonnet; дешевле с кэшированием каталога в промпте, Haiku для генерации gap/choice, Batch API для заготовок).
- Аутентификации, rate limit и Docker нет: личный инструмент, один пользователь. Ключи API и Supabase живут только на сервере и в клиент не попадают.
- День для лестницы повторений считается по часовому поясу сервера (`rating-model.md`, `DAY_START_HOUR`).

### Как сейчас устроен код

- Next.js 16 (App Router), React 19, TypeScript, Drizzle ORM + postgres-js, `@anthropic-ai/sdk`, `marked` (рендер `guide`), Langfuse + OpenTelemetry (трейсинг, ниже). База — облачный Supabase (`DATABASE_URL`), ключи в `.env.local`. Тесты — только чистых модулей (модель ученика, планировщик): `npm test`, встроенный `node:test` через `tsx`.
- Вместо API-роутов — server actions `src/app/actions.ts`, ошибки возвращаются значением:
  - задания: `startExercise(unitId, type|null)` (▶ в строке юнита), `checkExercise`, `revealExercise`;
  - сессия: `nextSessionExercise(workspaceId)` — задание по планировщику, `prepareNextExercise(workspaceId)` — заготовка следующего, пока решается текущее (в памяти сервера, в базу попадает только при показе), `sessionSummary(exerciseIds)` — итог сессии;
  - каталог: `setUnitStarted(unitId, started)`.
- `src/server/catalog` — модуль доступа каталога. `src/server/exercises` — типы, схема и запись лога. `src/server/tasks` — папка на тип (`<type>/index.ts` — `Task`: generate / parseAnswer / check; рядом md-файлы его промптов — `exercise-spec.md` §7), `prompt.ts` — чтение md и подстановка плейсхолдеров, `grade.ts` — проверка открытых ответов (вызов и нормализация, тексты — у типа), `variety.ts` — данные для разнообразия генерации (план фокуса, недавние задания), `claude.ts` — вызов модели (`askJson`, system с `cache_control`). `src/server/learner` — модель ученика, планировщик, показатели для каталога и итог сессии.
- **Трейсинг вызовов Claude — Langfuse Cloud.** Только трейсинг: промпты остаются в md в git, реестр промптов Langfuse не используется.
  - Каждый вызов `askJson` — отдельный трейс `generate` или `grade` с одной генерацией внутри: полный промпт (system и user), сырой ответ модели, фактическая модель (после fallback может отличаться от запрошенной — та в `requested_model`), токены с кэшем, время, стоимость (цены моделей Claude Langfuse знает сам), `stop_reason`.
  - Метаданные трейса: `call`, `type`, `prompt_version`, `unit_id`, `workspace_id`; у проверки ещё `exercise_id` и `seq` будущей попытки — `tasks/index.ts` пробрасывает их через контекст (`propagateAttributes`), а не параметрами.
  - Ошибки — та же генерация с уровнем `ERROR` и причиной в `statusMessage`: ошибка API, отказ, `max_tokens`, неразбираемый JSON.
  - Подключение — `src/instrumentation.ts` → `instrumentation.node.ts`: OTel `NodeSDK` с `LangfuseSpanProcessor` (`@langfuse/otel`, `@langfuse/tracing` v6). Режим `batched`: спаны уходят в фоне, ответ их не ждёт, недоступный Langfuse запрос не роняет. При остановке сервера трейсы, ещё не отправленные из буфера, могут потеряться — это допустимо: вызовов мало, сервер перезапускается вручную после сборки. Собственные OTel-спаны `@anthropic-ai/sdk` выключены, иначе генерация писалась бы дважды.
  - Ключи — `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL` в `.env.local`. Без ключей провайдер не регистрируется и трейсинг выключен: приложение работает как раньше, без ошибок и предупреждений.
  - Если вызов идёт внутри наблюдения Langfuse (прогон evals), генерация ложится в его трейс, а не в свой.
- **Evals — Langfuse Experiments**: настоящие вызовы промптов на фиксированных случаях с оценками; сравнивать версии промптов по цифрам, а не на глаз. Пока есть один набор — `gap-generate` (генерация gap).
  - Запуск: `npm run eval -- gap-generate grammar-in-use [--repeat N] [--report]` (`N` — сколько раз генерировать каждый случай, по умолчанию 1). Ключи Langfuse и Anthropic — из `.env.local`.
  - `--report` — подробный отчёт для калибровки судьи: markdown `evals/reports/<набор>_<область>_<время>.md` (папка в `.gitignore`). В начале — версии генерации и судьи и средние; по каждому заданию — юнит, тема, ошибка генерации, по каждому пункту — text, answers, focus, explain_ru и вердикт судьи целиком (все поля и note_ru; проваленные — жирным). Вердикты целиком лежат и в Langfuse — в metadata score `judge_rule`.
  - Случаи — `evals/<область>/<набор>.yaml` (`workspace_id` и `{id, unit_id, topic}`), источник истины — git: запуск синхронизирует их в датасет Langfuse `<область>/<набор>` (upsert, пропавшие — в архив). Набор — `evals/<набор>/index.ts` (задача и оценщики), общий запуск — `evals/run.ts`.
  - Задача — генерация без записи в базу: тема из случая, недавних заданий нет (`gap.generate(unitId, { topic, recent: [] })`). Имя прогона — версии промпта генерации и судьи и время.
  - Оценки по заданию (доля прошедших пунктов): кодом — `valid_items`, `answer_not_in_text`; LLM-судьёй (`claude-opus-5-5`, один вызов на задание, промпт `evals/gap-generate/judge.md` со своей версией, ответ — строго JSON) — `judge_rule`, `judge_key_complete` (пропущенные варианты — в comment), `judge_not_guessable`, `judge_aux_inside`, `judge_focus`, `judge_explain`. Оценки прогона — средние по каждому score. В терминал — средние и задания с проблемами по пунктам.
  - Повтор — один проход по всем случаям; его номер — `repeat` в metadata элемента прогона. При `--repeat N` по каждому score ещё среднее каждого повтора, min и max повторов — в терминале и в шапке отчёта; в Langfuse средние повторов — оценки уровня прогона `<score>/repeat-<k>` рядом с общими. Разброс повторов — шум модели: разница версий промпта в его пределах — не улучшение.
- `src/components/exercises` — UI заданий: общее для закрытых (`Exercise.css`, `useClosedCheck`, `CheckActions`), открытые — `OpenExercise` + `OpenAttempt`, обёртки типов (`RephraseExercise`, `TranslateExercise`, `FreeExercise`).
- Пользователь запускает prod-сервер (`npm start`): после `npm run build` его нужно перезапустить, иначе работает старый код.
- Разовые проверки — временным скриптом `scripts/_x.mts` (`npx tsx --conditions=react-server --env-file=.env.local scripts/_x.mts`), потом удалить. Пробные генерации — прямым вызовом `rephrase.generate` / `check`, без записи в базу, чтобы не трогать рейтинг.

### Порядок разработки
1. **Каталог, затем задания** — сначала каркас, таблица юнитов в Supabase, модуль доступа и страница каталога (`catalog-spec.md`), затем оглавление, потом перенос тренажёра (`claude-code-prompt.md`) поверх неё: юниты с первого дня по `id`. Генерация `guide` — когда удобно, до неё в промпт идёт `summary_ru`.
2. **Хранилище и лог попыток** — данные копятся с первого дня.
3. **Модель ученика** — эталонная реализация, сценарии из `rating-model.md` как тесты. Ручной режим: юнит выбирает пользователь, прогресс и сроки уже считаются.
4. **Планировщик + сессия по таймеру** — ежедневная сессия на 15 минут.
